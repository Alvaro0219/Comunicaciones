Qué hace cada parte del código del nodo GDA

Un ESP32 que mide la humedad del suelo y el clima del aire, los envía por internet y enciende una bomba de riego solo cuando el backend se lo ordena. Esta guía recorre el sketch de arriba abajo, en el mismo orden en que está escrito.

El nodo no decide

No tiene reglas de riego. Mide, informa y ejecuta lo que le piden.

La seguridad va primero

La bomba tiene un tope de tiempo y se apaga sola, pase lo que pase con la red.

Nada se queda esperando

El código evita quedarse bloqueado, para poder apagar la bomba a tiempo.

Cabecera y librerías

El bloque de comentarios del principio es el “manual” del sketch: dice qué es, qué hace y qué librerías hay que instalar. Después vienen los #include, que son las herramientas que el código toma prestadas.

LibreríaPara qué sirve
WiFi.h, WiFiMulti.hConectarse a WiFi. WiFiMulti permite guardar varias redes y elige la mejor disponible.
WiFiClientSecure.hConexión cifrada (TLS), necesaria porque HiveMQ Cloud exige el puerto seguro 8883.
ESPmDNS.hPermite encontrar la placa por nombre (gda-nodo1.local) en vez de por IP.
ArduinoOTA.hActualizar el programa por WiFi, sin cable USB.
PubSubClient.hHablar el protocolo MQTT (publicar y suscribirse).
ArduinoJson.hArmar y leer mensajes en formato JSON.
DHTesp.hLeer el sensor AM2302 (de beegee_tokyo, no la de Adafruit).
secrets.hArchivo aparte con claves WiFi, usuario y clave MQTT y clave OTA. Así no quedan en el código principal.

Ojo: secrets.h no está en lo que compartiste. Si no existe en la carpeta del sketch, no compila. Hay que crearlo a partir de secrets.h.example.

Configuración

Son constantes: valores que se ajustan una vez y no cambian mientras el programa corre.

Broker, identidad y prefijo

const char* MQTT_HOST = "...s1.eu.hivemq.cloud";
const int   MQTT_PORT = 8883;
const char* NODO_ID   = "nodo1";
const char* PREFIX    = "gda/prod";

MQTT_HOST y MQTT_PORT son la dirección del servidor MQTT. NODO_ID es el nombre de este nodo y debe coincidir con el de la maceta en el dashboard. MACETA_ID es el número de maceta que viaja dentro de cada mensaje.

PREFIX arma el “camino” de los mensajes. Con gda/prod el nodo usa el sistema real; con gda/dev-nombre alguien puede probar sin molestar a producción. Debe ser igual al TOPIC_PREFIX del backend.

Pines y calibración del suelo

El sensor de suelo va al GPIO 34, el AM2302 al GPIO 15 y el relé al GPIO 26. SUELO_SECO = 4095 y SUELO_MOJADO = 1925 son los valores crudos medidos con el sensor al aire y en agua. Cada sensor es distinto, así que hay que medirlos con el propio. LOG_CRUDO = true imprime el valor crudo en cada medición para facilitar esa calibración.

Ojo: el GPIO 15 es un pin que el ESP32 usa al arrancar. Si la placa no inicia con el sensor conectado, el propio comentario del código sugiere pasarlo al GPIO 4.

Tiempos y límites

ConstanteValorSignificado
AMBIENTE_MS5000Lee el AM2302 cada 5 segundos.
AMBIENTE_VIGENCIA_MS120000Si pasan 2 minutos sin una lectura buena, el dato de aire deja de enviarse.
DURACION_MAX_S120Tope duro de riego por orden: 2 minutos.
TELEMETRIA_MS30000Envía medidas cada 30 s (pruebas). En producción, 600000 = 10 min.

La constante RELE_ACTIVO_BAJO = true se explica en la sección del relé.

Certificado TLS

El bloque largo de letras entre BEGIN CERTIFICATE y END CERTIFICATE es el certificado raíz ISRG Root X1 de Let’s Encrypt.

En simple: es como llevar una credencial de la autoridad que firma el sitio. Cuando el ESP32 se conecta a HiveMQ, compara lo que recibe con este certificado y comprueba que realmente habla con HiveMQ y no con un impostor. Después, toda la conversación viaja cifrada.

Se usa más abajo, en net.setCACert(CA_CERT). Los certificados raíz tienen fecha de vencimiento; este indica 2035.

Objetos y estado

Aquí se crean los “aparatos” de software y las variables que recuerdan qué está pasando.

Objetos

WiFiMulti wifiMulti;          // maneja varias redes

Los tres topic_* son espacios de texto que se llenan en setup() con la ruta completa de cada canal.

Detalle técnico: el tiempo se mide con millis(), que cuenta los milisegundos desde que arrancó la placa. Todo el código usa este reloj en lugar de delay() largos.

Log: hablar por cable y por WiFi

void log(const String& msg) {
  Serial.println(msg);
  if (cliente && cliente.connected()) cliente.println(msg);
}

Cada vez que el programa quiere dejar un mensaje, lo escribe en el monitor serie (USB) y, si hay alguien conectado por telnet al puerto 23, también se lo manda ahí. Eso permite ver qué hace el nodo sin cable, desde otra computadora de la misma red.

Relé: el interruptor de la bomba

escribirRele(bool encender) es la única función que toca el pin del relé. Todo el resto del programa pasa por ella.

if (RELE_ACTIVO_BAJO) {
  if (encender) {
    digitalWrite(PIN_RELE, LOW);
    pinMode(PIN_RELE, OUTPUT);
  } else {
    pinMode(PIN_RELE, INPUT);   // pin flotante
  }
  return;
}
pinMode(PIN_RELE, OUTPUT);
digitalWrite(PIN_RELE, encender ? HIGH : LOW);

Muchos módulos de relé se activan con una señal baja (LOW), al revés de lo intuitivo. Además, si el módulo se alimenta a 5 V, los 3,3 V de un HIGH del ESP32 no alcanzan para apagarlo bien. La solución del código:

  • Encender: pone el pin en LOW y recién después lo convierte en salida.
  • Apagar: deja el pin como entrada, “flotando”, equivalente a desconectar el cable IN del relé.

Si tu módulo fuera activo-alto, se cambia RELE_ACTIVO_BAJO a false y se usa HIGH/LOW normales.

Sensor de suelo (FC-28)

leerHumedadSuelo() devuelve un porcentaje de 0 a 100.

  1. Promedia 10 lecturas, con 20 ms entre cada una (unos 0,2 s en total), porque este sensor es muy ruidoso.
  2. Convierte a porcentaje con map(), usando los valores de calibración. El rango está “invertido” a propósito: en el FC-28, un valor crudo más alto significa tierra más seca.
  3. Recorta el resultado con constrain() para que nunca salga de 0 a 100.

Probalo: de valor crudo a porcentaje

Mové el valor crudo y mirá el porcentaje que calcularía el nodo. Podés cambiar los valores de calibración.

0%

Detalle técnico: el GPIO 34 pertenece al convertidor ADC1 del ESP32, que sigue funcionando con el WiFi encendido. En setup() se configura en 12 bits (0 a 4095) y con atenuación de 11 dB para leer el rango completo de 0 a 3,3 V.

Sensor de aire (AM2302)

servicioAmbiente() se ejecuta en cada vuelta del programa, pero solo trabaja cada 5 segundos.

  1. Control de tiempo: si no pasaron 5 s desde la última lectura, sale sin hacer nada (así no frena al resto).
  2. Lee temperatura y humedad.
  3. Valida: sin error del sensor, sin valores “no numéricos” y dentro de rangos posibles (−40 a 80 °C, 0 a 100 %). Un dato imposible nunca llega al backend.
  4. Si es buena: la guarda, anota la hora y avisa “AM2302 recuperado” si venía fallando.
  5. Si es mala: cuenta la falla. Avisa en la primera y luego cada 12 fallas (aproximadamente cada minuto), para no llenar el log.

ambienteVigente() responde si la última lectura buena es lo bastante reciente (menos de 2 minutos). Si no lo es, la telemetría omite temperatura y humedad del aire.

En simple: prefiere no decir nada antes que decir algo viejo o inventado. Si faltan esos dos campos, el backend y el dashboard entienden que el sensor no responde.

Eventos: avisar que la bomba cambió

publicarEvento(bomba, motivo, duracionSeg) arma un mensaje JSON y lo manda al topic /evento.

{"maceta_id":1,"bomba":false,"humedad":58,
 "motivo":"fin de riego","duracion_seg":30,
 "commandId":"abc-123"}

Algunos campos son opcionales: la humedad solo va si ya hubo medición, la duración solo si es mayor a cero (son los segundos que la bomba estuvo realmente encendida) y el commandId solo si hay una orden en curso.

Qué pasa si no hay conexión

Si MQTT está caído, el mensaje no se pierde: se copia en eventoPendiente y loop() lo reenvía apenas vuelve la conexión. Es importante porque, sin el aviso de apagado, el backend creería que la orden falló.

Limitación: hay un solo lugar para guardar un evento pendiente. Si la conexión sigue caída y ocurre otro evento, el nuevo reemplaza al anterior. En un riego corto suele bastar (se pierde el aviso de encendido y queda el de apagado), pero no es una cola real.

Bomba: iniciar, detener y vigilar

Son tres funciones que trabajan juntas.

iniciarRiego(duracionSeg, commandId)

  1. Rechaza la orden si no trae una duración válida (menor a 1 s).
  2. Rechaza la orden si ya hay un riego en curso.
  3. Acota la duración a DURACION_MAX_S (120 s). El nodo nunca riega más que eso, aunque la orden pida más por error o por un bug.
  4. Mide la humedad en ese momento, para incluirla en el evento.
  5. Guarda el commandId y calcula el instante de fin: tBombaFin = inicio + duración.
  6. Enciende el relé, deja un mensaje en el log y publica el evento “bomba encendida”.

detenerRiego(motivo)

Si no hay riego, no hace nada. Si lo hay, primero apaga el relé y recién después hace todo lo demás (calcula cuánto duró, mide la humedad, escribe el log y publica el evento). Así, aunque algo se demore después, la bomba ya está apagada. Al final borra el commandId.

servicioBomba()

if (bombaEncendida && (long)(millis() - tBombaFin) >= 0) {
  detenerRiego("fin de riego");
}

Se llama en cada vuelta de loop(), antes que nada y sin depender de la red. Revisa si ya llegó la hora de apagar. La resta con conversión a long es un truco que sigue funcionando bien aunque millis() dé la vuelta al llegar a su máximo (a los ~49 días).

En simple: es como poner una alarma de cocina al encender la hornalla. La alarma suena aunque se corte internet, porque el reloj está dentro del nodo.

Telemetría: el informe periódico

publicarTelemetria() mide la humedad del suelo, arma un JSON y lo publica al topic /telemetria.

{"maceta_id":1,"humedad":58,
 "temp_ambiente":23.4,"hum_ambiente":61.0,
 "bomba":false,"rssi":-62,"ssid":"MiRed",
 "ip":"192.168.1.40","heap":210000}
CampoSignificado
humedadHumedad del suelo en %.
temp_ambiente, hum_ambienteAire, redondeados a un decimal. Se omiten si el sensor no responde.
bombaSi está encendida en este momento.
rssiIntensidad de la señal WiFi (más cerca de 0 es mejor).
ssid, ipA qué red está conectado y con qué dirección.
heapMemoria libre del ESP32, útil para detectar fugas de memoria.

Si mqtt.publish() falla, lo anota en el log como “Fallo publish”. A diferencia de los eventos, la telemetría no se reenvía: el siguiente informe llega en 30 s.

WiFi

cargarRedes() registra hasta tres redes (con sus claves desde secrets.h). conectarWiFi(), que solo se usa al arrancar, espera en un bucle hasta conectarse e imprime el nombre de la red, la IP y la señal.

Que espere ahí no es riesgoso: en ese momento el relé ya está apagado y no hay ninguna orden en curso.

MQTT: recibir órdenes y conectarse

onMessage(): cuando llega un mensaje

PubSubClient la llama automáticamente cada vez que llega algo al topic /comando.

{"activar_riego":true,"duracion_seg":5,"commandId":"..."}   // regar
{"activar_riego":false}                                     // detener ya
  1. Copia el contenido en un texto y lo escribe en el log.
  2. Lo interpreta como JSON. Si no se puede leer, lo informa y termina.
  3. Si no existe el campo activar_riego como verdadero o falso, lo ignora.
  4. Si es true, llama a iniciarRiego() con la duración y el commandId (si faltan, usa 0 y texto vacío).
  5. Si es false, llama a detenerRiego("orden de detencion"): es la parada de emergencia.

reconectarMQTT(): reconexión sin bloquear

Intenta conectar a lo sumo una vez cada 5 segundos y no se queda en un bucle de espera. Si conecta, se suscribe a /comando con QoS 1; si falla, anota el código de error (rc) y sigue.

Decisión de diseño: la sesión es “limpia” a propósito. Si el backend publicó una orden mientras el nodo estaba desconectado, esa orden no se entrega al volver. El comentario del código lo justifica: regar tarde por una orden vieja es peor que no regar.

Detalle técnico: el propio intento de conexión TLS puede tardar unos instantes. Pero es un intento puntual, no un bucle que espere indefinidamente.

setup(): el arranque

Se ejecuta una sola vez al encender la placa. El orden importa.

  1. Apaga el relé antes que nada, para que la bomba no arranque sola al encender.
  2. Abre el puerto serie a 115200 baudios y muestra el título.
  3. Configura el ADC: 12 bits y rango completo en el pin del suelo.
  4. Inicia el sensor AM2302 en el GPIO 15.
  5. Pone el WiFi en modo estación, carga las redes y espera la conexión.
  6. Activa mDNS para poder entrar como gda-nodo1.local.
  7. Configura OTA con nombre y contraseña. Si empieza una actualización, apaga el relé y marca la bomba como apagada. Durante la carga muestra el progreso, y al terminar o fallar lo informa.
  8. Inicia el servidor telnet en el puerto 23.
  9. Construye los tres topics con snprintf (por ejemplo gda/prod/nodo1/comando).
  10. Carga el certificado, indica el servidor MQTT, amplía el buffer de mensajes a 512 bytes y registra onMessage como la función que atiende los mensajes entrantes.

loop(): el ciclo que nunca termina

Se repite miles de veces por segundo. Cada paso es corto y casi todos tienen su propio control de tiempo.

  1. ArduinoOTA.handle(): atiende actualizaciones por WiFi.
  2. servicioBomba(): ¿venció el tiempo de riego? Va primero y no depende de la red.
  3. servicioAmbiente(): lee el AM2302 si toca. Tampoco depende de la red.
  4. Chequeo de WiFi cada 10 s. No se hace en cada vuelta porque wifiMulti.run() escanea redes y bloquea cerca de 2 segundos.
  5. Si no hay WiFi, la vuelta termina acá (return). Los pasos 2 y 3 ya se ejecutaron, así que la bomba se apaga a tiempo igual.
  6. Telnet: si llegó un cliente nuevo, cierra el anterior y acepta al nuevo.
  7. MQTT: si no está conectado, intenta reconectar; después mqtt.loop() procesa mensajes entrantes y mantiene la conexión viva.
  8. Evento pendiente: si hay uno guardado y MQTT está conectado, lo reenvía.
  9. Telemetría: la primera se envía apenas conecta, y luego cada TELEMETRIA_MS.

Por qué este orden: lo crítico (apagar la bomba) va arriba y sin depender de nada. Lo que puede fallar o demorarse (red, MQTT) va abajo.

Resumen: las protecciones de seguridad

Estas son las decisiones que evitan que la bomba quede encendida o se encienda cuando no debe.

RiesgoCómo lo evita el código
La bomba arranca al encender la placaEl relé se apaga como primera instrucción de setup().
Orden con duración excesivaTope de 120 s por orden.
Se cae WiFi o MQTT con la bomba encendidaEl apagado depende del reloj interno y se evalúa antes que la red.
Dos órdenes superpuestasSi ya hay riego en curso, la nueva se ignora.
Órdenes viejas al reconectarSesión MQTT limpia: no se entregan.
Datos de aire erróneosValidación de rangos y omisión del dato si es viejo.
Actualización OTA con bomba encendidaEl relé se apaga al iniciar la actualización.
Se necesita parar de inmediatoComando {"activar_riego":false}.
Cosas a tener presentes al modificar el código

El commandId se copia con strncpy a un espacio de 48 caracteres y se recorta si es más largo. Los mensajes JSON de eventos y telemetría caben en buffers de 256 y 320 bytes; si agregás muchos campos, hay que agrandarlos. El buffer MQTT de 512 bytes también limita el tamaño de los mensajes.

La lectura del suelo bloquea unos 200 ms. Es aceptable acá, pero conviene tenerlo en cuenta si se agregan más sensores.
