Guía del código de GDA

Cómo funcionan el backend, el frontend y la base de datos, cómo se hablan entre sí y con el broker, y por qué elegimos cada tecnología. Pensada para que cualquiera del grupo pueda explicar el sistema y defender sus decisiones.

1. Visión general

El sistema son cuatro piezas que se hablan por canales distintos. El backend está en el centro: es el único que conoce a todos.

Cinco ideas para tener siempre presentes

  1. El nodo mide y ejecuta; el backend decide.El ESP32 no tiene reglas de riego. Envía lo que mide y obedece órdenes. Toda la inteligencia (umbrales, lluvia, esperas) vive en el backend, y se puede cambiar sin tocar el hardware.
  2. El backend es un cliente MQTT más.No hay un broker propio: usamos HiveMQ Cloud. El nodo y el backend se conectan a él desde cualquier red y el broker reparte los mensajes.
  3. Para pedir, REST; para enterarse, SSE.El dashboard pide datos con llamadas HTTP normales y recibe novedades en vivo por una conexión SSE que el backend mantiene abierta. Por eso la pantalla se actualiza sola.
  4. MongoDB guarda todo, y el historial es la fuente de verdad.Lecturas, riegos, alertas y órdenes quedan registrados. Toda decisión, incluso la de no regar, deja un evento.
  5. El frontend no decide nada de negocio.Muestra lo que el backend calcula y manda pedidos. Las reglas de riego, las alertas y los permisos reales se aplican en el servidor.

2. Backend

Node.js con Express, organizado en capas. Cada capa tiene una sola responsabilidad, y eso permite seguir cualquier funcionalidad de arriba hacia abajo.

Estructura de carpetas

Regla de oro de las capas

Las rutas llaman a controladores, los controladores a servicios y los servicios a modelos, y nunca al revés. Si hay que explicar «dónde está» algo: la URL está en routes, la regla de negocio en services y la forma del dato en models.

Cómo arranca (app.js)

El archivo app.js arma la aplicación y la pone en marcha. Los middlewares se aplican en este orden, y el orden importa:

  1. CORS: solo deja llamar a la API desde los orígenes configurados (el frontend).
  2. morgan (registro de pedidos), helmet (cabeceras de seguridad) y el lector de JSON.
  3. Límite global de uso sobre /api (1000 pedidos cada 15 minutos).
  4. Rutas de la aplicación y, al final, el manejador global de errores.

Después conecta a MongoDB, abre el puerto, conecta el cliente MQTT pasándole dos funciones (handleTelemetry y handleNodeEvent) e inicia las tareas programadas.

El recorrido de un pedido HTTP

Todos los endpoints siguen el mismo camino. Ejemplo con «Regar ahora»:

// routes/pot.routes.js
router.post('/:id/irrigate', irrigationLimiter, authenticate, canManage,
            validate(irrigateSchema), irrigatePot);

Dos detalles que ordenan el código:

  • Los controladores no tienen try/catch. Se envuelven con asyncHandler, que manda cualquier error al manejador global. Así los errores tienen un único formato.
  • Toda respuesta tiene el mismo formato: { success: true, data } o { success: false, error: { message, code } }. El frontend se apoya en eso.

Servicios principales

Acá está el corazón del sistema. Abrí cada uno para ver qué hace, qué recibe y qué produce.

mqtt/client.jsLa conexión con el broker

Se conecta a HiveMQ por TLS y se suscribe a {prefijo}/+/telemetria y {prefijo}/+/evento (el + significa «cualquier nodo»). Cuando llega un mensaje, saca el nodeId del topic y llama al servicio que corresponda.

Entra
Mensajes MQTT del nodo (telemetría y eventos de la bomba).
Sale
Órdenes de riego publicadas en {prefijo}/{nodeId}/comando.
Detalle clave
Los mensajes de un mismo nodo se procesan de a uno y en orden (una cola por nodo). Sin eso, el evento de la bomba y la telemetría podrían registrar el mismo riego dos veces.
Reglas de equipo
Cada persona usa su propio MQTT_CLIENT_ID y su prefijo gda/dev-nombre. Con MODO_ESCRITURA=false el backend nunca publica órdenes: solo el desplegado puede regar la bomba real.
services/ingestService.jsProcesar cada lectura que llega

Función principal: handleTelemetry(nodeId, mensaje). Es lo primero que se ejecuta cuando el nodo manda datos.

  • Busca la zona activa con ese nodeId. Si no existe, descarta el mensaje y avisa en el log.
  • Normaliza el mensaje (acepta los nombres en español del firmware) y valida: la humedad del suelo fuera de 0–100 % deja la lectura como inválida; una temperatura imposible se descarta sola.
  • Guarda la lectura en Reading. Si ya existía (mismo nodo y misma hora), la ignora: así una retransmisión no duplica nada.
  • Actualiza el resumen de la zona (lastReading, online), cierra la alerta de «fallo de sensor» si estaba abierta y avisa a los navegadores por SSE.
  • Si la lectura es válida y tiene menos de 10 minutos, llama al motor de decisión.
Mensaje sin humedad
Se trata como un «latido» de diagnóstico: actualiza señal WiFi, IP y memoria, pero no crea lectura ni decide nada.
services/decisionService.jsEl motor de decisión de riego

Función principal: evaluateReading(zona, lectura). Compara la lectura con los límites de la zona y decide. Las reglas, en orden:

// resumen de la lógica (no es código literal)
si humedad < mínimo:
    si zona exterior y llueve en 6 h:
        pospone + alerta preventiva
        // salvo: emergencia (cae 10 puntos bajo el mínimo)
        //        o espera máxima superada (6 h) → riega igual
    si no: riega + alerta crítica
si humedad > máximo: no riega + alerta de exceso
si temperatura ≥ umbral y humedad < mínimo + 10: alerta de calor + riego breve
si no: cierra las alertas de humedad que estuvieran abiertas
  • Espera entre riegos: después de regar espera 10 minutos (DECISION_COOLDOWN_MIN) porque el suelo tarda en reflejar el agua. Sin eso regaría en cada lectura.
  • Todo queda registrado: cada decisión crea un Event, incluso «no regar» o «pospuesto».
  • Zonas interiores: ignoran el pronóstico de lluvia.
  • Lectura del clima: solo del caché; nunca llama a la API externa en medio de una decisión.
services/irrigationService.jsOrdenar, ejecutar y confirmar un riego

triggerIrrigation es el único emisor de órdenes: lo usan tanto el motor automático como el botón manual. Así los dos caminos pasan por las mismas protecciones.

  • No emite si el backend está en modo lectura (deja un evento «riego omitido») ni si ya hay una orden pendiente para esa zona.
  • Crea una IrrigationCommand con un identificador único (commandId) y publica la orden por MQTT.
  • handleNodeEvent recibe lo que publica el nodo al encender y al apagar la bomba. Solo ese evento confirma un riego; la telemetría nunca lo hace, porque podría ser anterior a que el nodo reciba la orden.
  • Al confirmar guarda la duración real que reportó el nodo y actualiza «último riego».
  • expireStaleCommands (tarea programada) marca como expiradas las órdenes sin confirmación pasada la duración más un margen.
  • simulateDemoIrrigation: el riego de las zonas de ejemplo es simulado y no publica nada.
services/weatherService.jsPronóstico con caché

Consulta Open-Meteo con la latitud y longitud de la zona y guarda el resultado en la colección WeatherCache. La clave es la ubicación redondeada a 2 decimales, así zonas cercanas comparten el mismo pronóstico.

  • getForecast devuelve el caché si tiene menos de 3 horas; si no, consulta la API. Si la API falla, devuelve el último caché disponible.
  • rainExpected mira las próximas 6 horas y compara la probabilidad máxima con el umbral de la zona.
  • Una tarea programada refresca todas las ubicaciones cada 3 horas.
services/alertService.js y notificationService.jsAlertas y emails
  • raiseAlert crea una alerta solo si no hay ya una activa del mismo tipo para esa zona. Esto evita repetir alertas y emails mientras la condición sigue.
  • Si el dueño tiene activado el email y ese tipo de alerta, sendAlertEmail lo envía con Nodemailer. Sin servidor SMTP configurado, solo lo escribe en el log.
  • resolveAlerts cierra alertas cuando la condición desaparece, y avisa por SSE.
realtime/sseHub.jsEmpujar novedades al navegador

Mantiene la lista de navegadores conectados. broadcast(tipo, datos, dueño) manda un evento a todos los que corresponde: el administrador recibe todo y el resto solo lo de sus propias zonas. Cada 25 segundos manda un «ping» para que ningún intermediario corte la conexión.

Eventos que se emiten: reading, event, alert, alert_resolved y pot_status.

jobs/scheduler.jsTareas que corren solas
  • Cada minuto: checkSensorTimeouts busca zonas sin datos por más de 15 minutos, las marca sin conexión y levanta la alerta de fallo de sensor (las zonas de ejemplo se excluyen).
  • Cada minuto: expireStaleCommands expira las órdenes sin confirmar.
  • Cada 3 horas: refresca el pronóstico de todas las ubicaciones.

3. El ciclo de riego, paso a paso

Es el camino que cruza casi todo el backend. Si pueden explicar esto con los archivos, entienden el sistema. Hacé clic en cada paso.

Cómo se cierra el círculo

Cuando el backend recibe el evento del nodo y confirma la orden, emite novedades por SSE. El navegador las recibe y actualiza la tarjeta («Regando…», «Último riego») sin recargar. El riego manual hace el mismo recorrido desde el paso 5, salteando la decisión automática.

4. API REST y seguridad

Todos los endpoints cuelgan de /api. Esta tabla se puede filtrar por texto o por rol.

MétodoRutaQuién puedeQué hace

«Quién puede» indica el rol mínimo. Los técnicos y visualizadores solo ven y operan sus propias zonas; el administrador ve todo.

Cómo se protege

Autenticación con JWTDos tokens: uno corto y uno de renovación
  • Al iniciar sesión, authService verifica la contraseña con bcrypt y entrega un access token (corto, con el rol del usuario) y un refresh token (más largo).
  • Cada pedido lleva Authorization: Bearer <token>. El middleware authenticate lo verifica y deja los datos del usuario en req.user.
  • Cuando el access token vence, el frontend usa el refresh token para pedir uno nuevo, sin que el usuario lo note.
  • Las contraseñas nunca se guardan: se guarda su hash con bcrypt.
Roles y alcance por dueñoQuién puede hacer qué y sobre qué
  • requireRole(['admin','tecnico']) bloquea el pedido con 403 si el rol no corresponde. El visualizador no puede crear, editar ni regar.
  • potScope(req) devuelve el filtro que se agrega a toda consulta sobre zonas: vacío para el administrador y { ownerId: usuario } para el resto. Así nadie ve ni opera zonas ajenas aunque adivine un identificador.
// middlewares/auth.js
export function potScope(req) {
  return req.user.role === 'admin' ? {} : { ownerId: req.user.sub };
}
Validación y límites de usoSe rechaza lo que no cumple antes de llegar al controlador
  • Joi (carpeta schemas/) define qué campos se aceptan, de qué tipo y en qué rango. validate(schema) descarta campos desconocidos y responde 400 si algo no cumple.
  • rate limit: 10 intentos de login cada 15 minutos, 10 órdenes de riego por minuto y 1000 pedidos generales cada 15 minutos.
  • helmet agrega cabeceras de seguridad y CORS limita desde qué sitios se puede llamar a la API.
Conexión en vivo (SSE) y su tokenPor qué no se usa el mismo token de siempre

El navegador no permite enviar cabeceras en una conexión SSE, así que el token tendría que viajar en la URL. Para no exponer el token de sesión, el frontend pide primero uno efímero (POST /api/stream/token, dura unos 60 segundos y solo sirve para SSE) y lo usa para abrir la conexión. Si se corta, pide otro.

Secretos y configuraciónQué nunca está en el repositorio

Contraseñas de la base, del broker, claves de los tokens y del correo viven en el archivo .env (ignorado por git) o en secrets.h del firmware. Solo config/env.js lee las variables de entorno y las valida con Joi; el resto del código importa ese módulo. Se versiona únicamente .env.example, con valores de ejemplo.

Decisiones de diseño que conviene saber explicar

Por qué el estado actual está dentro de la zonalastReading, watering, lastIrrigation

El dashboard necesita mostrar muchas zonas rápido. Si para cada tarjeta hubiera que buscar la última lectura en una colección con miles de documentos, sería lento. Por eso la zona guarda una copia (un «resumen») de su último estado, que se actualiza con cada lectura. El historial completo sigue en Reading.

Idempotencia de las lecturasEl índice único evita duplicados

El índice único por nodo y hora de medición hace que guardar dos veces la misma lectura sea imposible. Cuando el nodo reenvía lo acumulado tras un corte, MongoDB rechaza las repetidas y el código simplemente las ignora.

Gráfico de 24 horas agregado en la base$group y $dateTrunc

Con lecturas cada pocos segundos, pedir «las últimas N» devolvería solo las más recientes. El endpoint /readings/recent agrupa las lecturas en intervalos y devuelve unos 300 puntos que cubren toda la ventana. Cualquier endpoint que sirva series largas al frontend debería hacer lo mismo.

Borrado lógicoisActive en lugar de borrar

Eliminar una zona primero la desactiva: deja de procesar datos pero conserva el historial. Recién una zona ya desactivada puede eliminarse definitivamente, y ahí se borran también sus lecturas, eventos, alertas y órdenes.

Caché del pronóstico en la baseWeatherCache

Guardar el pronóstico evita llamar a la API externa en cada decisión y permite seguir funcionando si Open-Meteo no responde. Zonas cercanas comparten el mismo documento.

Cómo fluye un dato: de la pantalla al backend y de vuelta

Piezas que conviene saber explicar

Sesión y renovación automáticastores/auth.js y el interceptor de Axios
  • Al iniciar sesión, los tokens y el usuario se guardan en la tienda de Pinia y en localStorage (clave gda_session), así la sesión sobrevive a recargar la página.
  • Un interceptor de Axios agrega el token a cada pedido. Si el backend responde 401, intenta una sola vez renovar la sesión con el refresh token y repite el pedido. Si falla, cierra la sesión y vuelve al login con el aviso «sesión expirada».
  • El getter canOperate (admin o técnico) decide si se muestran los botones de crear, editar y regar. Es solo comodidad visual: el backend vuelve a validar el permiso.
Rutas protegidasLa guarda del router

Antes de cada cambio de página, la guarda revisa: si la ruta es pública deja pasar; si no hay sesión, manda al login; si la ruta exige un rol (como /dashboard/users, solo administrador) y el usuario no lo tiene, lo manda al dashboard. Las pantallas se cargan de forma diferida (lazy loading), solo cuando se visitan.

Tiempo real con SSEcomposables/useRealtimeStream.js
  • Al montar la pantalla pide un token efímero y abre una conexión EventSource.
  • Recibe un objeto con funciones por tipo de evento (reading, event, alert, alert_resolved, pot_status) y llama a la que corresponde con los datos recibidos.
  • Si la conexión se corta, espera 3 segundos, pide un token nuevo y reconecta. Al salir de la pantalla cierra la conexión.
  • El indicador «En vivo» del dashboard refleja el estado de esta conexión.
Una sola fuente de verdad del estado de una zonautils/potState.js

La función potState convierte los datos de una zona en un estado visible (sin conexión, regando, seca, húmeda, en rango). La usan la tarjeta, la tabla, el detalle y los filtros del dashboard, para que todos muestren lo mismo.

Diseño responsive: tabla en escritorio, tarjetas en celularcomponents/ResponsiveTable.vue

Un solo componente recibe las columnas y las filas. En pantallas de 1024 píxeles o más dibuja una tabla; en pantallas menores dibuja una tarjeta por registro, con la primera columna como título. Lo usan las pantallas de Zonas, Usuarios y los tres historiales del detalle.

Formularios y diálogosAppDialog y PotDialog

AppDialog es la carcasa común de todos los diálogos (encabezado con ícono, cuerpo con scroll y pie con acciones; en celular ocupa toda la pantalla). PotDialog la usa para crear y editar zonas, agrupando los campos en secciones: identificación, humedad deseada (con un deslizador de rango), lluvia, calor y ubicación.

Identidad visualPaleta, tipografías y MoistureBand

Los colores y las fuentes se definen una sola vez como variables CSS (--gda-*) en styles/app.css. Quasar toma sus colores de marca de quasar-variables.sass. El componente MoistureBand dibuja la banda de humedad deseada con un marcador que cambia de color según esté seca, en rango o húmeda: es la regla central del sistema hecha visible.

El contrato MQTT

Los topics tienen el formato {prefijo}/{nodeId}/{tipo}. El prefijo separa entornos: gda/prod es solo del nodo real y del backend desplegado, y cada integrante usa el suyo (gda/dev-nombre) para no pisarse.

TopicDirecciónMensaje (JSON)
…/telemetrianodo → backend{ maceta_id, humedad, temp_ambiente, hum_ambiente, bomba, rssi, ssid, ip, heap }
…/comandobackend → nodo{ activar_riego: true, duracion_seg: 5, commandId }
…/eventonodo → backend{ maceta_id, bomba, humedad, motivo, duracion_seg, commandId }, al encender y al apagar la bomba
  • Las suscripciones y las órdenes usan QoS 1: el broker garantiza que el mensaje llega al menos una vez.
  • El commandId viaja en la orden y vuelve en el evento, y así el backend sabe con exactitud qué orden se confirmó.
  • El detalle completo del contrato está en docs/ESP32_CONNECTION_GUIDE.md.

Conviene decirlo nosotros antes de que lo pregunten: es un prototipo, y estos son sus límites conocidos.
